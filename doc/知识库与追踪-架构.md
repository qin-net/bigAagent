# 知识库与追踪：架构

> 状态：**K0–K2 已实现**（跟踪心跳未做）  
> 日期：2026-08-27  
> 位置：本仓库 `doc/`  
> 本文只冻结结构。作业清单、书目、卡片主题不在这里。  
> 运行时细节仍以 `Agent运行时框架设计.md` 为准；首次研究仍以现有四专家 workflow 为准。

---

## 1. 系统里有谁

五个角色，**不是六个**。综合决策、编排、校验、落盘是 Python 系统环节，不包装成 Agent。

| 角色 | 职责 | 读文献 | 写方法论 | 研究某只票 |
|---|---|---|---|---|
| 基本面 / 技术面 / 情绪 / 宏观 | 本维报告 | 否 | 否 | 是：只读快照 + 已批准卡片 |
| 追踪 | 知识库管理者；以后按增量调度四专家 | 是：只读本机已转写的章节 md | 只写 `candidate` | 蒸馏轮次不研究个股；跟踪轮次才碰 thesis |

经管只交付原文。人不写卡片。人不做全书校对。批准是人，不是任何 Agent。

追踪 **只有一个**：蒸馏和跟踪调度共用同一 System、同一 `AgentState` 类型、同一模型。差别只在本轮 **Task** 和本轮打开的工具集。禁止再做一个「蒸馏 Agent」。

---

## 2. 知识三层（运行时只碰 L1 已批准）

```text
L0 原料     PDF/HTML → 本地 md     不进 analyze Prompt，不进向量库
L1 卡片     短条目 + 版本          仅 approved 可被 search_methodology 命中
L2 手册     以后：链到 approved     不进专家 System
```

真人索引（Wiki）属于 L0 的目录，给人溯源。Agent 运行时 **不读 Wiki 页面**。

全书 embedding RAG 不做。向量若以后出现，只给 L1 已批准卡片的标题/触发词做同义词，且必须再过字段门。

---

## 3. 两条运行时，不要混

```text
                    ┌──────────── 首次 / U2 反馈 ────────────┐
                    │  workflow 并行四专家                    │
用户代码 + 口语 ──► │  专家工具：snapshot / search_methodology │
                    │  决策是模板，不是第五个投票专家          │
                    └────────────────────────────────────────┘

                    ┌──────────── 追踪 Agent ─────────────────┐
离线选中的一章 md ─►│  Task=蒸馏  读 md → submit_candidate     │
以后：增量事件 ────►│  Task=跟踪  0～4 个 AgentSkill → 交付物  │
                    │  两 Task 都不能 approve / 改专家 System   │
                    └────────────────────────────────────────┘
```

首次研究 **不叫醒** 追踪。U2 反馈是人对报告说话，走原 workflow 子 run，不是追踪。

追踪蒸馏轮次 **不注册** 四专家 AgentSkill。跟踪轮次默认不读 L0；需要新纪律时再开蒸馏 Task，不在心跳里顺手喂全书。

---

## 4. 数据与权限

两库继续分开：`insightagent.db` 持有 `methodology_entries` / `methodology_versions`、Run、Report；`board.db` 持有行情。知识原件在本机目录，gitignore，**不把 PDF 发给模型**。

```text
L0 md（白名单路径）
        │ 仅追踪·蒸馏 Task
        ▼
methodology_entries     status: candidate | approved | retired
methodology_versions    改文只追加 version；旧 Report 钉死当时 version
        │ 仅 approved
        ▼
search_methodology(scope, query, flags)  → 0～3 条短文
        │ 仅四专家 + 追踪自己查重时
        ▼
Report.citations.kb_id  必须 ∈ 本轮工具返回
```

工具权限：

- 四专家：`search_methodology` 只读 approved、本 `scope`；无写库、无读 L0。  
- 追踪蒸馏：读白名单 md、读已有条目（含 candidate 以便去重）、`submit_candidate`。无 `approve`，无跨角色改 Report。  
- 批准：系统 CLI/以后审核页，代码闸门，不交给 LLM。  
- 用户 `#remember`：只进 `UserPreference`，禁止写入方法论表。

---

## 5. L1 卡片合同（检索键，不是文章）

一条卡片是可版本化的纪律对象，用 Pydantic 合同入库，不再传松散字典。旧字段迁移：`evidence_required` → `applicability.any_flags`，`trigger` → `retrieval.canonical_terms`，`priority` → `retrieval.priority`，`action/text/exceptions` → `guidance`。

至少包括：稳定 `id`、`scope`、`type`、`status`、`version`，以及：

- `applicability`：`any_flags` / `all_flags` / `none_flags` / `required_fields`  
- `retrieval`：`canonical_terms` / `aliases` / `intent_tags` / `priority` / `mandatory`  
- `guidance`：`action` / `text` / `exceptions`  
- `source_refs`：出处与 sha  
- `tests`：`should_match` / `should_not_match` fixture  

约束：

- `scope` 与检索角色必须相交；基本面搜不到技术面条目。  
- `any_flags` / `all_flags` / `none_flags` 必须是快照上 **已冻结的 flag 名**。对不上的草稿不得入库。  
- `text` 有硬顶；`action` 是检查，不是买卖指令。  
- `id` 批准后不改，只升 `version`。

蒸馏模型把章节收成这种对象；它不把章节留在运行时索引里。

## 6. 命中（analyze 侧）

专家先读本维预计算快照，再调用 `search_methodology`。核心原则：**事实决定哪些卡片可用，词汇只决定可用卡片之间的相关程度。**

顺序：

1. `status=approved` 且 `scope` 含本角色  
2. **applicability 硬过滤**：`all_flags` 全中、`any_flags` 有交（若非空）、`none_flags` 全不中；`required_fields` 仅在调用方传入 `present_fields` 时检查  
3. 在可用集合上打分：`mandatory` +1000、命中 flag ×100、canonical ×20、alias ×10、intent ×10、再加 `priority`  
4. 模型 `query` 与用户 `intent_tags` **只参与第 3 步**，不能把未过硬过滤的卡片召回来  
5. 按分数截断最多 3 条  

蒸馏查重仍可 `flags=None`，只对 canonical/aliases 做关键词去重。

工具返回：

```json
{
  "retrieval_id": "kb-search-01",
  "entries": [
    {
      "id": "kb_cashflow_lag",
      "version": "1",
      "title": "利润需要经营现金流验证",
      "text": "...",
      "action": "...",
      "score": 1220,
      "reasons": ["mandatory", "flag:cashflow_lag", "alias:利润含金量", "version:1"]
    }
  ]
}
```

报告引用的 `kb_id` 必须出现在 **这一次** `entries` 里，否则丢掉。部分 flag 可另加「必须引用」的校验，那是证据绑定，不是检索算法。

## 7. 蒸馏（追踪侧，结构对称）

输入：一章级 md + 目标 `scope` + 该 scope 允许的字段名表。  
输出：0～N 条 `candidate`，以及冲突/去重说明（可进追踪自己的 state / process 记录）。

硬限制：单轮上下文只含这一章，不含整本、不含 PDF、不含四专家。提交前用字段表校验；重复 `id` 只能提案升 version，不能静默覆盖 approved 正文。

人审过的才 `approved`。没有「蒸馏成功即上线」。

---

## 8. 跟踪期怎么接（同一架构往后长）

跟踪不改 L0/L1 模型。只给追踪换 Task、加工具：增量摘要、`TrackingContext` 只读、四专家 AgentSkill、写出 `TrackingDeliverable`。

调度仍是事件路由、能不叫专家就不叫。方法论：跟踪轮次只 **检索** approved；发现过程问题只 **提交** candidate。批准、改权重、改专家 System 仍禁止。

看板行情是跟踪的数据面，不是知识库。Agent 读板是适配，不替代 L1。

---

## 9. 和现有模块的边界

| 已有 | 与本文关系 |
|---|---|
| 四专家 + 决策模板 + U2 | L1 的消费者；不改专家互辩、不改决策公式 |
| 口语意图 / 偏好 | 约束 Task；不是 L1 |
| SQLite 方法论表 | 已建，写入与检索尚未接到 analyze |
| 看板 | 独立数据面；研究入口另篇；不在本文展开 |

---

## 10. 分期（只到架构落地顺序）

1. **检索闸门**：空查询不返回、scope、截断、未检索 kb 丢掉（可仍读内存条）。  
2. **L1 接库**：内存条迁入版本表；import / show / approve。  
3. **追踪蒸馏 Task**：白名单读 md、submit_candidate；四专家仍不读 L0。  
4. **跟踪 Task**：同一 Agent 加 AgentSkill 与心跳。  
5. **可选**：L1 同义词向量；L2 手册页。

前三步不依赖跟踪心跳。第四步不另起 Agent。

---

## 11. 明确不做

```text
第二个蒸馏专用 Agent
分析 Agent 读 PDF / 全书 md / Wiki
L0 chunk 向量当知识库
自动 approved
用事后涨跌晋升条目
偏好写入方法论
蒸馏或跟踪轮次改专家 System / 买卖权重
首次研究里叫醒追踪
```
