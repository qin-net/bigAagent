# 从"空引用"到四层修复：一次 bug 的完整追踪报告

日期：2026-10-18
用通俗语言记录：问题怎么被发现、怎么被定位、怎么被修复、修的过程中又暴露了什么。
不涉及函数名，面向"想知道发生了什么"的读者。

---

## 一、一句话概括

用户问了一句「引用是什么意思」，顺着这个问题追下去，发现了一条完整的问题链：
**检索工具在某种情况下必定返回空 → 模型被迫编造引用 → 校验的兜底又恰好放行编造**。
一共涉及四层，全部修复并验证，另外顺手补了 7 张知识库卡片。

---

## 二、问题是怎么被发现的

### 第 1 步：一个普通的问题

用户问："引用是什么意思，你是说找卡片吗？我没理解，什么是非知识库类和知识库类的？"

这时我要解释系统里的"引用"机制，于是去读了引用校验的代码。

### 第 2 步：读代码时发现异常

代码逻辑是：

```
删掉"本轮没检索到"的卡片引用
  ↓
如果删完一条不剩，而且报告不是弃权 → 把非卡片类引用捞回来
  ↓
如果连非卡片类也没有 → 原样返回【未过滤的报告】
```

最后一步明显不对：它的效果是"**引用全被删光时，把所有删掉的引用原样恢复**"。

### 第 3 步：停下来，不猜

我没有直接说"这里写错了"，而是**写了一段最小复现**：

```python
# 本轮检索到的卡片集合是空的
retrieved = set()
# 报告里两条引用，都是卡片类，都是编的
report.citations = [kb_cashflow_lag, kb_INVENTED_NOT_IN_DB]
drop_unretrieved_kb(report, retrieved)
# 期望：应该是空的或弃权
# 实际：两条都被原样保留
```

结果确认：**假引用完整通过**。

### 第 4 步：追问"为什么会走到这一步"

一个关键疑问浮出来：模型为什么会编造引用？

因为规则要求"非弃权报告必须有引用"，模型手里又没有真卡片。那**为什么一张卡片都没有**？

继续往上追，发现了检索工具的问题：

- 检索需要两个输入：查询词 + 这只股票的特征标签
- 特征标签为空时（股票没触发任何异常或机会模式）
- 代码把它当成"筛选条件为空集合"，而空集合与任何条件都没有交集
- 于是 **109 张卡片全部淘汰 → 返回零结果**

### 第 5 步：确认因果链

```
股票没触发任何特征
  ↓
检索把空特征当成空集合 → 零结果（且不解释原因）
  ↓
规则要求"必须有引用"，模型没有真实卡片可用
  ↓
模型编一个卡片编号凑格式
  ↓
校验发现是编的，删掉
  ↓
删空了 → 兜底分支"别删了吧" → 原样放回
  ↓
一份完全建立在编造依据上的报告，通过校验，写进库，展示给用户
```

**这不是四个独立的小毛病，是一条首尾相接的链。**任何一环做对，都不会发生。

## 三、修复：四层，一层一层来

用户确认后，定下四层修法，逐层实现。

### 第 1 层：检索工具——空特征时改为按查询词匹配

**改什么**：把"特征为空"理解为"这只股票没触发信号"，而不是"用空集合去筛"。特征为空时，退化成按查询词搜索。

**为什么这样改**：一只各项指标都正常的股票，本来就应该能查到"这种情况该怎么评估"的卡片。原来它一张都查不到，等于系统对"正常的公司"最没有方法论支持——这本身就说不通。

**验证**：
- 空特征 + 查询"现金流" → 命中现金流相关卡片（原来返回空）
- 空特征 + 只查"检查清单" → 命中兜底卡

### 第 2 层：检索结果——零结果时明确说明原因

**改什么**：检索返回的数据结构里加一个"说明"字段。零结果时填上：
"本次没有适用方法论卡片，请不要编造卡片编号，改用快照字段、计算指标或规则命中作为依据，并在报告中说明无适用卡片。"

**为什么**：模型会编，很大程度是因为没人告诉它"空是正常的、可以有别的出路"。给它一个诚实的台阶，它就未必会撒谎。

**验证**：零结果时说明字段有内容；正常命中时说明字段为空（不干扰正常情况）。

### 第 3 层：兜底卡片——让"没命中"也有真话可引

**改什么**：
1. 卡片契约新增"永远适用"标记（原来强制要求每张卡必须挂触发条件，兜底卡塞不进去）
2. 新增三张兜底卡：
   - 基本面：没有触发特定模式时的基础财务检查
   - 技术面：没有特定形态时的趋势与位置检查
   - 情绪/宏观：没有重大事件时的信息真空处理
3. 兜底卡优先级压到最低（10，正常卡是 60-100），**只在没有其他卡片匹配时才出场**，不会挤掉真正的规则

**为什么**：用户提的思路——"没命中就放行"不对，但"给一张真的适用于无模式情况的卡片"是对的。区别在于：前者允许说假话，后者让真话有得说。

**验证**：批准后，空特征查询能命中兜底卡；正常卡存在时兜底卡不出场；跨维查询仍然返回空（隔离没有被破坏）。

### 第 4 层：校验——堵死"过滤后原样返回"的后门

**改什么**：
- 删掉"引用全被删光就原样返回"的分支
- 改为：删掉假引用后，在缺失信息里注明"有 N 条引用未能在本轮检索中命中，已剔除"，并把报告标记为降级
- 如果一条真凭据都不剩，**整份报告转为弃权**——宁可不下结论，不给一个建立在编造依据上的结论
- 顺带修掉一个隐藏问题：原来用浅拷贝改字段生成新报告，而浅拷贝**不会重新跑校验**，导致那句"防止校验崩"的 try/except 是死代码。改成完整重建，让校验真正生效

**验证**：
- 全是编造引用 → 引用清零、转为弃权、标记降级、写明剔除原因
- 真假混合 → 只删假的、保留真的、标记降级但不下弃权

## 四、修复过程中又暴露了什么

### 1. 契约挡出了我写的第三张卡

给"估值中性"写卡时，它只有排除条件（"估值不便宜也不贵时适用"），没有触发条件。而契约强制要求必须挂触发条件，直接拒绝。

**这说明契约本身有个缺口**：只靠"排除条件"限定的卡片是合法且常见的（"当 A、B、C 都不成立时"），契约应该允许。

已补：`any_flags / all_flags / none_flags / always_applicable` 四者有一个即可。

### 2. 我自己的第一版改法错了两次

- **第一次**：让兜底卡无条件参与所有匹配。结果跨维查询（用技术特征查基本面）会返回兜底卡，破坏了维度隔离。测试直接抓到。
- **第二次**：让兜底卡在有特征筛选时也放行。结果同样破坏隔离，测试再次抓到。

**最终规则**：
- 空特征 → 退化成关键词匹配（兜底卡凭自己的词命中）
- 有特征 → 严格按特征筛，兜底卡不参与
- 关键词模式 → 兜底卡和普通卡一样要通过关键词匹配

这两次翻车值得记下来：**"让它永远可用"听起来很好，但会破坏系统里已有的边界**。测试在这里救了我两次。

### 3. 一条过时的测试期望

有个测试断言"空特征必须返回空"——这正是这次要改的行为。判断依据是：这条断言描述的是**旧的错误行为**，不是系统的真实意图。所以更新了断言，并在注释里写明原因。

### 4. 一个还没解决的检索细节

中文查询往往不带空格（"估值合理区间"），而关键词匹配是按空格切词的，所以整句查询匹配不到卡片里的"合理区间"。这次没有临时改，记在这里，作为后续优化项。

| 事件兜底卡 | 兜底 | 无事件时的信息真空处理 |

### 仍然存在的缺口

| 优先级 | 缺口 | 说明 |
|---|---|---|
| 高 | 薄覆盖标签 | `insufficient_bars` 只有 1 张、`valuation_rich` 2 张、`has_inquiry` 2 张 |

| 中 | 情绪维疑似重复 | 43 张卡覆盖 7 个标签，其中"无重大事件"一个标签 29 张，密度异常，建议人工抽查合并 |
| 低 | 中文无空格查询 | 检索的切词方式对中文不友好 |

### 补卡建议

**资料优先级**：

1. **你自己的文档**（最优）——《个人投资决策手册》《基本面Agent规则FUND》《技术面规则》，这次的 7 张卡基本都来自它们
2. **官方监管文件**（针对具体标签）——问询函、减持、业绩预告的合规口径
3. **不建议**：券商研报、自媒体、投资书籍——那些是观点不是规则，会让专家把别人的判断当约束

**写法建议**：

- 每张卡都写 `should_match` 和 `should_not_match`，特别是后者——"什么时候不该用这张卡"比"怎么用"更重要
- 只写"该怎么做"而不写边界，是补卡最容易犯的错

## 六、这次排查方法上值得留下的东西

### 1. 不猜，先复现

四条最关键的发现（跨用户泄漏、假引用放行、压缩标记从未生效、空特征零结果）**全部经过实际运行验证**，不是读代码推断的。

复现的成本很低——写十几行脚本，几分钟。但它把"我觉得有问题"变成了"我证明有问题"。

### 2. 审计 agent 的输出要打折看

四个审计 agent 一共报了约 120 条。逐条核对后发现：

- 大部分有价值
- 少数是误报（例如"四处 SQL 注入"，实际全是固定字面量，不可注入）
- 一些是推测（标注了"推测"的，要单独对待）

**报告长度不代表问题严重程度**。真正致命的只有 7 条。

### 3. 工具也有它的边界

静态检查工具（lint）在十分钟内扫出了十来个真问题，包括一个会导致崩溃的"名字未定义"。但它扫不出"某段分支从未被执行"这类逻辑问题——那需要人读代码 + 端到端验证。

### 4. 测试这次救了我两次

我第一版和第二版改法都破坏了维度隔离，两次都被现有测试当场抓住。**好的测试不只是防止旧 bug 回归，也是修改时的护栏。**
