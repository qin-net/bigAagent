## 二、P0 级：并发正确性

### P0-1 模拟盘下单丢失更新

**问题**

`BoardStore.paper_trade`（原 `store.py:554` 起）的写法是「先读账户现金 → 在 Python 里算 → 再 UPDATE 写回」：

```python
with self._connection() as connection:
    account = dict(connection.execute("SELECT * FROM paper_account WHERE user_id=?", (user_id,)).fetchone())
    cash = float(account["cash"])
    ...
    connection.execute("UPDATE paper_account SET cash=? WHERE user_id=?", (cash, now, user_id))
```

而 `_connection()` 用的是 `sqlite3` 默认的 **deferred** 事务模式，且上下文管理器本身不显式开启事务。

**后果**

SQLite 的 deferred 事务**在 SELECT 阶段不加锁**，隐式 `BEGIN` 要等到第一条写语句才发生。
实测（本机 SQLite）：

```
in_transaction after SELECT: False
in_transaction after UPDATE: True
```

也就是说「读现金」完全发生在事务之外。FastAPI 的同步端点跑在线程池里，两个并发下单请求会**都读到同一份余额**，各自扣减一次并各自写回，最终只扣了一次钱却成交两次 → 虚拟账户被超额买入（现金可能变成负数或持仓超过资金能力）。

单用户本地看板触发概率低，但这是实打实的资金账目错误，且是「越多人用越错」的静默错误。

**根因**

「先读后写」不是原子操作，且未显式加写锁。同文件中的 `claim_research` 已经用 `BEGIN IMMEDIATE` 正确处理过同类问题，此处遗漏。

**改法**（`store.py:602-604`）

在读账户之前显式取得写锁：

```python
with self._connection() as connection:
    # BEGIN IMMEDIATE: the cash/position read must happen inside the write
    # transaction, or two concurrent orders both see the same balance.
    connection.execute("BEGIN IMMEDIATE")
    account = dict(...)
```

`BEGIN IMMEDIATE` 在「读」之前就取得 RESERVED 写锁，使得并发的第二个事务在 `BEGIN` 处等待，从而串行化整个「读-算-写」过程。

**验证方式**

5 线程并发对同一标的各下 100 股（初始资金仅够 1 手）：

```
results: ['ok', 'insufficient virtual cash', 'insufficient virtual cash',
          'insufficient virtual cash', 'insufficient virtual cash']
cash: 5000.0  position qty: 100
```

仅 1 笔成交，余额正确扣减，其余 4 笔被正确拒绝。

### P0-2 深度采集队列重复领取

**问题**

`BoardStore.claim_deep`（原 `store.py:387`）同样是「SELECT 一条 pending → UPDATE 成 running」，中间没有 `BEGIN IMMEDIATE`。

**后果**

`claim_research` 写了 `BEGIN IMMEDIATE`，`claim_deep` 没写。而系统的实际部署形态是：`insightboard worker` 为**独立进程**，`serve` 内部还会再起一个 worker **线程**（`__main__.py` 中 `threading.Thread(target=_run_research_worker)`）。因此「两个领取者同时 SELECT 到同一行」是真实可触发的竞态，不是理论风险。后果是同一只股票被重复采集深度数据（重复的网络请求、重复写库、`attempts` 计数翻倍提前耗尽重试额度）。

**改法**（`store.py:431-433`）

加入 `BEGIN IMMEDIATE`，与 `claim_research` 保持一致。另外修正返回值：原实现返回的是 UPDATE 之前的行（`status` 仍是 `queued`、`attempts` 是旧值），调用方拿到的与库中实际状态不一致；现改为返回按 UPDATE 结果修正后的字段（`status='running'`、`attempts+1`）。

**验证方式**

`ruff` 与既有测试套件通过；并发行为与 `claim_research` 采用同一已验证模式。

## 三、P0 级：数据完整性

### P0-3 公告表去重失效（主键含可空列）

**问题**

```sql
CREATE TABLE notice_headline (
    stock_code TEXT NOT NULL,
    title TEXT NOT NULL,
    published_at TEXT,          -- 可空
    ...
    PRIMARY KEY (stock_code, title, published_at)
);
```

**后果**

SQLite 对普通表（非 `WITHOUT ROWID`）的 PRIMARY KEY 列**不隐式加 NOT NULL**，且 **NULL 之间互不相等**。
因此 `save_deep` 中的 `INSERT OR REPLACE INTO notice_headline ...` 对于没有发布时间的公告**完全不起作用**——同一条公告每采集一次就新增一行，公告表无限膨胀（每次采集都写入，且 `notices()` 按 `published_at DESC` 排序取出，重复项会挤占前 30 条展示位）。

实测：同一条 `published_at=NULL` 的公告连续插入 3 次，得到 3 行。

**改法**（`store.py:101-109`、`137-160`、`134`）

1. 建表 DDL 改为 `published_at TEXT NOT NULL DEFAULT ''`：
   - 新库直接以正确结构创建；
   - 非空后主键的「NULL 互不相等」问题消失，`INSERT OR REPLACE` 恢复去重语义。
2. 插入时归一化：`n.published_at or ""`，避免上游返回 `None` 时触发 NOT NULL 约束错误。
3. 为**已有旧库**增加一次性重建迁移 `_repair_notice_headline`：检测 `PRAGMA table_info` 中 `published_at` 的 `notnull` 标志，若为旧结构则用 `BEGIN IMMEDIATE` + 建新表 + `INSERT OR IGNORE ... SELECT COALESCE(published_at,'') ... ` + `DROP` + `RENAME` 原子重建，顺带把历史重复行折叠掉。

> 实现细节：迁移中**不能**用 `executescript`。`executescript` 会先隐式提交当前事务，导致重建不再原子；因此改为逐条 `execute`。另外 `initialize()` 在此函数之前已执行过 INSERT，会隐式开启事务，故先 `connection.commit()` 再 `BEGIN IMMEDIATE`，否则报 `cannot start a transaction within a transaction`（该问题在验证阶段已发现并修正）。

**验证方式**

- 新库：同一公告（`published_at=None`）连续插入 3 次 → 表中仅 1 行。
- 旧库：手工构造可空主键的旧表并塞入 3 行重复数据 → `initialize()` 后收敛为 1 行，且重复调用 `initialize()` 幂等、不报错。

## 四、P0 级：流程与可用性

### P0-4 追踪任务失败后 run 永久 `running`

**问题**

`track_thesis`（原 `tracking_agent.py:1075-1299`）整体**没有任何 try/except**。而其中的 `agent.run()`、`fetch_track_snapshots()`、`store.save_timeline()`、`_prepare_intent()` 任一步抛出异常，函数都会直接向上冒泡，而 `track_run.status = "success"` 位于函数末尾（原 1287 行）——**永远不会被执行**。

**后果**

- 该 run 永久停留在 `status="running"`，形成脏记录；
- `_resolve_track_parent` 要求父 run 的 `status in {"success","degraded"}`，因此这条 thesis 的**后续追踪与反馈链被彻底卡死**，用户无法继续追踪；
- 失败没有任何 `run_failed` 审计事件，排障时只能看到 run 一直「在跑」。

对比：`analyze_stock` 有完整的失败兜底（标记 `failed` + 写 `run_failed` 审计），追踪路径漏了。

**改法**（`tracking_agent.py:1161` 起，`1301-1312`）

把 `track_thesis` 的主体（从 `_prepare_intent` 导入处到 `TrackResult` 返回）整体包进 `try`，并补齐与 `analyze_stock` 同构的失败处理：

```python
except Exception as error:
    track_run.status = "failed"
    track_run.updated_at = utc_now()
    await store.save_run(track_run)
    await audit.append(
        "run_failed",
        {"type": type(error).__name__, "message": str(error)},
        run_id=track_run.run_id,
    )
    raise
```

保留 `raise` 让调用方（CLI / 队列 worker）仍能感知失败，但不再留下脏 run。

**验证方式**

`py_compile` 通过，`pytest` 全绿（含 `test_tracking_full_chain.py` 等追踪链路测试）。

### P0-5 研究 worker「超时」不生效

**问题**

```python
with ThreadPoolExecutor(max_workers=1) as pool:
    future = pool.submit(execute_job_sync, item, store)
    try:
        result = future.result(timeout=timeout_seconds)
    except FutureTimeout:
        store.finish_research(item["job_id"], error="研究超时，请再点一次分析或追踪")
```

**后果**

`with ThreadPoolExecutor(...)` 语句退出时会调用 `shutdown(wait=True)`，**一直等待那个已经跑飞的任务结束**。因此：

1. 8 分钟超时后虽然给前端写了一个「失败」，但 worker 循环本身仍然被阻塞在 `shutdown` 上，**后续排队任务不会被领取**，整个研究队列停摆；
2. 该任务最终仍会执行完并往 agent 库写出一个**成功的 run**，与 board 库中的 `failed` 状态互相矛盾；
3. 提示文案「请再点一次」在这个状态下也不会成功（任务仍在占用）。

**改法**（`insightboard/__main__.py:97-115`）

不再使用 `with`，改为显式管理 executor，超时后**不等待**：

```python
pool = ThreadPoolExecutor(max_workers=1)
future = pool.submit(execute_job_sync, item, store)
try:
    result = future.result(timeout=timeout_seconds)
except FutureTimeout:
    store.finish_research(item["job_id"], error="研究超时，已继续处理后续任务；可稍后重试")
    pool.shutdown(wait=False)   # 不阻塞 worker 主循环
else:
    store.finish_research(...)
    pool.shutdown()
```

同时把用户提示文案改为符合实际的表述。

**验证方式**

`pytest` 全绿；行为上超时后 worker 能立即领取下一个任务。

> 遗留：这是「止血」方案。彻底解法是（a）给任务加取消机制，或（b）由子进程执行并支持 kill。见第六节。

### P1-1 `import insightboard.api` 的隐藏副作用

**问题**

`api.py` 末尾有模块级 `app = create_app()`，而 `create_app()` 会创建并初始化数据库、读取 `.env`。

删除模块级 `app = create_app()`。已确认全仓无 `insightboard.api:app` 形式的引用（`__main__.py` 与测试均使用 `create_app(...)` 工厂）。

**验证方式**

### P1-2 外键约束从未生效

**问题**

`PRAGMA foreign_keys` 是**连接级**设置（不像 `journal_mode=WAL` 是持久属性），必须在每个连接上设置。原实现只在 `initialize()` 里设置了一次，而 `_connection()` 每次新建连接时没有设置。

**后果**

`schema` 中声明的 `REFERENCES`（如 `quote_snapshot.batch_id REFERENCES quote_batch(batch_id)`）在**所有正常读写路径上从未生效**，外键约束形同注释。数据一致性完全依赖应用层自觉。

**改法**（`store.py:29-34`）

在 `_connection()` 中每个连接都执行 `PRAGMA foreign_keys=ON`，并补上显式的 `timeout=5.0`（busy timeout），与 `persistence.py` 的做法对齐。

**验证方式**

`pytest` 全绿（既有看板测试 + 数据完整性测试）。

### P1-3 Python 3.9 下的 asyncio 原语绑定问题

**问题**

`asyncio.Semaphore` / `asyncio.Lock` 在构造函数中被创建：

- `resources.py`：`CallOrchestrator.__init__` 里 `asyncio.Semaphore(max_parallel_calls)`
- `state.py`：`InMemoryStateStore.__init__` 里 `asyncio.Lock()`
- `persistence.py`：`SQLiteDatabase.__init__` 里 `asyncio.Lock()`

在本机 Python 3.9 上，这些原语在构造时会绑定当前事件循环（`get_event_loop()`），若构造发生在事件循环之外或前一个循环已关闭，就会在后续使用时抛出：

```
RuntimeError: There is no current event loop in thread 'MainThread'.
```

**后果**

实测：测试套件整体运行时 **5 个测试失败**（`test_macro_agent`、`test_sentiment_agent`、`test_technical_agent` 的注册测试与 `test_kb_split` 两个用例），而这些用例**单独运行时全部通过**——典型的测试间污染，会掩盖真实回归。生产侧同样存在「在循环外构造、在循环内使用」时报错的隐患。

**改法**

三者统一改为**惰性创建**：

- `resources.py:216` 新增 `_parallel_gate()`，`_semaphore` 首次使用时才创建
- `state.py:76` 新增 `_mutex()`，替换全部 `async with self._lock`
- `persistence.py:274` 新增 `_init_mutex()`，`initialize()` 内部使用

均加注释说明「Python 3.9 下 asyncio 原语绑定当前事件循环」这一约束，以及由此推出的「实例不应跨事件循环复用」。

**验证方式**

测试套件整体运行：5 个失败用例全部转为通过（详见第七节）。

## 六、P2 级

### P2-1 危险脚本加门禁

**问题**

`scripts/run_live_picks_research.py` 的 `main()` 一进来就无条件调用 `clear_demo_tracks()`，而该函数实际执行的是：

```python
DELETE FROM research_job WHERE kind IN ('track', 'track_feedback')   -- 删除全部追踪作业
DELETE FROM tracking_timeline                                        -- 删除全部追踪时间线
DELETE FROM runs WHERE mode = 'track_day' OR run_id LIKE 'demo-%-track'
```

函数名暗示「只清理 demo」，但前两条语句删除的是**全部**追踪记录；且无 `--yes`、无 `--dry-run`、无备份、路径不可覆盖。

**后果**

任何人（包括未来的你自己）手滑跑一次这个脚本，本地全部追踪历史即被删除且不可恢复。

**改法**（`scripts/run_live_picks_research.py`）

- 增加 `argparse` 与 `--reset-tracks` 开关，**默认不执行**清理，并打印提示；
- 模块 docstring 明确标注该开关是破坏性操作。

**验证方式**

默认运行打印「skipping track cleanup」；`--help` 可查看说明。

## 八、遗留问题（本轮未修，按优先级）

本轮采取「止血优先」，以下问题已定位但未修改，建议后续按序处理：

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| 高 | 研究作业**租约无心跳**：`recover_research(older_than_minutes=8)` 会把跑超 8 分钟的 running 作业打回 queued，而执行期间没有任何续租动作 | 长任务被另一个 worker 重新领取并**并行执行**，两个作业写同一 thesis |
| 高 | `user_store` / `methodology` 的多语句写入未包事务（`isolation_level=None` 自动提交） | 中途异常导致「偏好已退休但新偏好未写入」等数据丢失 |
| 高 | `runs` / `reports(run_id)` / `decisions(run_id)` / `tracking_timeline(run_id)` / `user_utterances` 等表**缺索引** | 全表扫描，随数据量增长持续劣化 |
| 中 | worker 超时为「放弃等待」而非「取消任务」 | 跑飞任务仍会写出与 board 库矛盾的成功 run（见 P0-5 遗留说明） |
| 中 | DDL 三处定义且互相矛盾（`persistence.MIGRATION_*`、`methodology.METHODOLOGY_DDL`、`BoardStore.initialize*`） | 同一张表的外键约束因创建顺序不同而不同 |
| 中 | 行情层无进程级限流与 TTL 缓存；`financials` 被重复拉取两次 | 触发数据源频控，浪费请求 |
