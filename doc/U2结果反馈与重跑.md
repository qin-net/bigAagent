## 0. 结论

在 `analyze_stock` **打出终稿之后**，允许用户再提一段 prompt。处理方式与开跑前相同：程序剥 tag → LLM 抽六槽 → 按 `effect` 分流。要改结论必须带 `#rerun` / `#重跑`。只 `#记住` 不重跑。普通 `this_run` **不许改已经落盘的报告**。

不引入主 Agent。仍是 Python workflow。跟踪期的行情增量调度不在本期。

默认 **复用父 run 的四份 snapshot**，只重跑被点名的分析维，再 **追加一条新 Decision**。旧 Report / 旧 Decision 冻结。实现上用 **新 `run_id` 挂同一 `thesis_id`**，避免当前 `report_id = {run_id}-{agent}` 的 `INSERT OR REPLACE` 把旧行盖掉。

## 1. 为什么挂在首次 workflow，不挂跟踪

| | 结果反馈（U2） | 跟踪 |
|---|---|---|
| 触发 | 人看完报告不满意 | 时间到了 / 价格或事件相对 thesis 变了 |
| 输入 | 用户 prompt + 可选 tag | 增量行情、旧 falsifier |
| 调度方 | 首次研究的 Python 函数 | 追踪 Agent（未做） |
| 快照 | 默认沿用当时那份 | 新拉 delta |

用户偏好约束的是 **怎么分析这只已指定的票**，不是按偏好选下一只。

## 2. 产品形态

首次 `analyze` 成功后，CLI 在终稿末尾多一行提示（失败 run 不提示）：

```text
可对本次结果反馈：python -m insightagent feedback <run_id> --prompt "..."
```

```text
python -m insightagent analyze 000858 --prompt "#remember #fundamental 估值对照经营现金流，不要只看PE"

python -m insightagent feedback 258d74c2-... \
  --prompt "#rerun #fundamental 经营现金流为负可能是中报季节性，对照往年中报再判，不要直接当成质量崩了"
```

`feedback` 的 `--prompt` 默认 `"none"`：空则退出码 0、不抽槽、不写库、不重跑。

不做：`analyze` 进程内阻塞等第二句（不好做脚本/评测）；无限多轮聊天界面。同一 thesis 上可以多次 `feedback`，每次一条新 run，父指针指向 **上一次成功的研究或反馈 run**（见 §5）。

stdout 必须并排能看懂「反馈前 / 反馈后」：打印父 Decision 的 rating/confidence 与新 Decision，以及本次实际重跑了哪些维。完整 JSON 仍写 `data/runs/{新run_id}.json`。

## 3. 分流（与偏好设计 §9 对齐，moment 改为 post_decision）

抽槽、tag 词表、不存原话、用户句只进 Task：全部复用 U1。`_prepare_intent` 增加 `moment` 参数；`feedback` 传 `post_decision`。

先看 `effect`，再看槽位 / 维度 tag。

### 3.1 `this_run`（默认）

记 utterance + intent。不写 preference。不重跑。不改父 run 任何行。

语义：这句话留给 **下一次** 真的开跑（下一次 `analyze` 或下一次带 `#rerun` 的 `feedback`）时并进对应维 Task。当前已结束的父报告不受影响。

六槽全 `none`：合法空操作。

### 3.2 `remember`

每个非 `"none"` 的维槽写一条 `UserPreference`（现有 `persist_remember`）。不重跑、不改父报告。下次同 `user_id` + 同维 +（本票或 `stock_code=none`）自动注入。

### 3.3 `rerun`

只调度下面集合里的分析维（`fundamental` / `technical` / `sentiment` / `macro`）：

```text
要重跑的维 = 槽位 != "none"  的维  ∪  被维度 tag 点名的维
```

该维槽若仍是 `none`，Task 只带已有 active 偏好 + 默认 instruction。  
该维槽非 `none`：按 U1 规则进 `required_questions` / `constraints`，并带上该维偏好（最多 8×80 字）。

未在父 run 跑过的维：本次等于该维第一次跑（仍用父 snapshot；没有快照则本维弃权并记 audit）。

只点 `#decision`（或仅 `intent.decision != none`）且四个分析槽全 `none`、也没有分析维 tag：**只重跑决策模板**，专家一个不动。输入是父 run 已落盘的四份 Report（缺的维仍按决策函数现有缺维逻辑）。`user_constraint` = 当次 decision 槽 + scope=decision 的偏好。

`#rerun` 但六槽全 `none` 且 `tags == ["none"]`：不调度，不当失败。audit `rerun_noop`。

`intent.tracking != "none"`：仍忽略（无追踪 Agent）。

### 3.4 `remember_rerun`

先 3.2 再 3.3。重跑 Task 必须已经能读到刚写入的偏好。

## 4. 重跑时用什么证据

**默认：不重拉 AKShare。** 从父 run 的 `snapshot_refs` 读回四份 artifact，反序列化成与首次相同的 snapshot 对象，工具仍指向这份冻结数据。

理由：反馈针对的是「当时那份报告怎么看」，不是「现在行情变了没有」。后者是跟踪。

可选旗标 `--refresh-snapshot`（默认关）：才重新 fetch。打开时 audit `snapshot_refreshed`，新 artifact 挂在 **新 run** 上，父 run 的 refs 不动。本期实现可以先不做这个旗标，文档留口；没做则 CLI 遇到该旗标直接报错退出。

禁止：把用户反馈原文、抽槽短句写进 Evidence / citations。`not_evidence` 槽仍只做抽取侧说明，不进报告。

## 5. 落盘与 ID

当前 `ResearchStore.save_report` / `save_decision` 的主键绑死 `run_id`，同一 run 再存会替换。U2 **不要**在父 run 上覆盖。

```text
父 run（首次或上一次反馈）
  reports / decision 冻结

子 run（本次 feedback）
  run_id          新 uuid
  thesis_id       与父相同（如 000858-initial）
  mode            "research"
  status          success | failed | ...
  parent_run_id   写入 runs.payload_json（RunRecord 若无该字段：只放 payload，不改表结构）
  snapshot_refs   默认复制父的；--refresh 才换新
  session_ids     仅写入本次实际重跑的维（新 session）
```

本次没重跑的维：**子 run 的 Report 行仍要有**，内容从父 run **拷贝**（同一 JSON，新 `report_id`），好让 `build_multi_factor_decision` 和 `--json` 自洽。拷贝不是重推理。audit `report_copied`，payload 含 `role`、`from_run_id`。

决策：子 run 一条新 Decision。父 Decision 不 UPDATE。展示层「反馈前」读父，「反馈后」读子。

失败：子 run `status=failed`，父 run 保持原 status。不要回滚已经写下的 preference（remember 已先落盘的，保持；与 U1「抽取失败不写偏好」不同——这里 remember 成功、后面专家挂了，偏好仍然有效）。

## 6. Session

本期 **每个被重跑的维新建 session**，不复用父 session 的对话。专家 System、工具集、输出 schema 与首次相同。

不复用的原因：父 session 里已有一次 `submit_final`，再追加 user 容易变成「改口」而不是「按新约束再交一份」；也避开 runtime 对终态 session 的假设。

session 按 agent+stock+thesis 复用：明确 **不在 U2 做**。以后要省 token 再开，且必须规定：复用时仍要新的 `submit_final`，旧 Report 仍不改。

---

## 7. 决策怎么重算

与首次同一函数 `build_multi_factor_decision`。

输入：子 run 上四份 Report（重跑的是新的，未重跑的是拷贝）+ 当次 `user_constraint`。

宏观相关度 low 弃权、情绪无窗口事件弃权且不 degraded：沿用现有编排规则，不要为反馈另写一套。

rationale 允许加一句前缀：`基于 run {parent_run_id} 的反馈重跑：{重跑的维列表}`。不要把用户原话拼进去。

## 8. 成本（必须守的）

这是记忆/反馈这条线的考查点：token、时间、有没有用对偏好。

| 规则 | 做法 |
|---|---|
| 空 prompt | 零 LLM |
| 只 remember / 只 this_run | 最多一次抽取（thinking 关），零专家 |
| 只 `#rerun #decision` | 一次抽取 + 零专家 + 一次模板 |
| 点名一维 | 一次抽取 + **一个**专家 + 一次模板 |
| 禁止 | 无 tag 无槽还把四维全重跑 |
| 快照 | 默认不重拉网 |
| 偏好 | 仍每维最多 8 条、每条 80 字；旧的截断 |

无维度 tag 且 LLM 把用户抱怨填进了某一维：以抽取结果为准，只重跑那些非 none 维。这是可接受的；不要再让程序猜「他一定是在喷基本面」。

`AnalysisOutcome.to_dict()` 增加只读字段（没有就放 outcome 旁路 JSON，避免硬改合同引发大面积测试）：`parent_run_id`、`rerun_dimensions`、`copied_dimensions`、`parent_decision` 摘要。能从 payload 推断的可不加字段。

测试（FakeLLM，不要 live）：

1. `feedback` + prompt `none`：无新 intent、无新 run。  
2. `this_run` 有槽：有 utterance，父 decision rating 不变，无新专家调用。  
3. `#remember` 无 rerun：preference 增加，无新专家。  
4. `#rerun #fundamental`：只有基本面 LLM 被调；技术/情绪/宏观 report 与父 JSON 一致；新 decision 存在；父 decision 行仍在。  
5. `#rerun` 且 tags/槽全 none：noop。  
6. 父 run 不存在或 status=failed：明确错误，不造子 run。  
7. 原话不出现在 user_* 表（沿用 U1 测法）。

## 10. 反例

| 错误 | 正确 |
|---|---|
| 反馈默认改旧报告 | 新 run、旧行冻结 |
| 没 `#rerun` 就重推理 | `this_run` / `remember` 不动结论 |
| 一次反馈四维全跑 | 只跑点名或非 none 维 |
| 用户句进 citations | 只进该维 Task |
| 用盈亏/涨了跌了自动写偏好 | 禁止；人可以说「对照季节性」，那是口径不是监督信号 |
| 把这做成追踪 Agent | 追踪是行情增量；这是人对报告的口径 |
| analyze 进程里死等第二句 | 独立 `feedback` 子命令 |
| 同一 run_id 再 save_report | 会 REPLACE 旧行 |

## 12. 给经管的一句话

系统先出一份可追溯的首次报告；你可以对着报告再下一句（记住口径，或点名某一维按新口径重跑）。旧结论留着对照，新结论另存。不是改聊天记录，也不是让系统自己去挑下一只股票。
