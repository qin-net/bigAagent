# bigAagent 问题复盘：为什么会有这么多 bug

日期：2026-10-16
范围：四轮深度排查（编排层 / 运行时内核 / 数据获取层 / 看板前后端）的合并复盘

---

## 〇、先看数字：别被条数吓到

四轮排查一共列出约 120 条发现。这个数字需要拆开看：

| 级别 | 条数 | 含义 |
| --- | --- | --- |
| 致命 | 7 | 会坏数据、漏隐私、误导投研结论 |
| 高 | 12 | 会让某个功能直接失效 |
| 中 | 约 40 | 边界情形、体验缺陷、口径不一致 |
| 低 | 约 60 | 可维护性、样式死代码、无障碍 |

两点必须说清：

1. **这是第四轮扫描的结果。** 每一轮都要求"排除已知项，再挖更深"，所以交上来的必然是长尾。同样的方法对着任何一个两万行的项目跑，结果不会更短。
2. **只有约 15-20 条经过逐条复核**（在本文中标注为「已复核」）。其余为排查结论，含推测与不可达路径，也可能有误报。实际例子：某轮报告"四处 SQL 注入"，逐条核对后确认全部是误报（查询用的是固定字面量）。

**结论：清单长度不等于代码质量。真正要处理的是那 19 条，其中好几条是一行改动。**

## 一、根因总结：只有 5 个模式

120 条发现，追到根上反复出现的就是这 5 个模式。**修掉它们，这类问题会断崖式下降。**

### 模式一：写了，但没验证"它到底生效了吗"

这是最核心、最普遍的一条。

代码里有大量**看起来周全、实际从不执行**的分支：

- 消息压缩时有个"关键消息要保留"的标记，全仓**只有读取、没有写入**——所以这个保护从来没生效过。
- 用户反馈的"留给下一次用"标记，只有一处写入、**零处读取**——所以承诺的"下次生效"从未发生。
- 某个降级重试，判断条件恒为真，实际执行的是"把刚失败的调用原样再跑一遍"。
- 一个数据库版本号写进去之后，**没有任何代码读它**。
- 一处异常处理是"捕获后原样抛出"，语义上等于没写。

**共同点：写完代码之后没有回头问一句"这段在真实流程里跑到了吗"**。人眼看代码时，这种"永不生效的分支"极难发现——因为它写得像模像样。

**改法**：对每一段"保护性/兜底性"代码，要么加断言证明它会被触发，要么用日志/审计事件证明它**真的在被执行**。这次排查中"审计事件"正是发现问题的利器——凡是写了审计的地方，行为都能被还原；凡是没写的，出问题就是黑盒。

### 模式二：兜底逻辑开成了后门

为了保护"不崩溃"，在最危险的场景放行了错误数据。最典型的是引用校验：

- 本意：报告只能引用真实检索到的卡片。
- 兜底：过滤完若一条不剩，怕校验失败，于是**把编造的引用原样保留**。
- 结果：**恰好在"引用全是编造"这个最该拦截的场景，系统放行。**

同类还有：严格的数据格式校验失败后，不是报错，而是**悄悄降级成一个空对象、再标记成"成功"**，让整条链路以为数据齐全。

**改法**：兜底的目标是"不崩溃"，不是"不报错"。过滤后为空时应当**诚实地降级**（标记降级 + 记录原因）或**转成弃权**，绝不允许"放行明知有问题的数据"。

### 模式三：异常被吞掉，故障伪装成"没有数据"

系统里有大量"出错了就当没有"的处理，且**全仓没有日志**（看板层三万多行代码里零日志，只有 print 和吞异常）：

- 采集公告失败 → 静默返回空列表 → 页面显示"暂无公告"。你**永远分不清**是"确实没公告"还是"接口挂了"。
- 用户画像查询数据库出错 → 静默返回空 → 页面显示"专家还没有记忆"。用户以为专家什么都没学到，实际是数据库故障。
- 解析你的口语意图时，网络超时、密钥失效、返回格式错，全部塌缩成同一个"格式不合法"。结果是**你所有的口头要求被静默丢弃，分析照跑不误**，你还以为它听懂了。

**改法**：区分"业务上确实没有"与"技术上失败"。前者正常返回，后者必须**可见**（至少一条日志，最好能反馈到界面）。这条改动成本极低、收益极大。

### 模式四：并发默认"不会同时发生"

大量代码建立在乐观假设上——同一时刻只会有一个人/一个进程在做事：

- 读余额、算、再写回，中间**没有锁**。两个请求同时下单，各自读到同一份余额，各自扣一遍 → 账目错。
- 任务队列的领取，同一个文件里**有的地方记得加锁、有的地方忘了**。忘掉的地方，两个 worker 会领到同一个任务，重复执行。
- 长任务没有"我还活着"的信号，超时后被打回队列，被第二个 worker 抢走并行执行。

**共同点**：作者知道正确的写法（同一个文件里就有正确范例），但在赶工时漏了一处。**正确性依赖"每次都记得"，而不是依赖机制。**

**改法**：把"必须加锁"变成"想忘也忘不掉"——统一的事务入口、统一的队列领取接口。这也是本次已完成的改动方向。

### 模式五：护栏缺失 + 赶工冲刺

- **零 lint、零 CI、零依赖版本约束**。所以"导入了但没用"、"用了但没导入"、"变量定义了没用"这类问题可以长期潜伏——本次一加检查工具，立刻扫出十来个，其中包括真会导致崩溃的"名字未定义"。
- **冲刺式提交**。8 月 31 日一天七个提交，当天代码正是本次问题最密集的区域（模拟盘事务、前端转义、危险脚本、超时失效全部出自那几天）。而更早、更慢的看板基础开发期，代码质量明显更高。
- **同一作者在同一项目里写出两套标准**：内核层（Agent 运行时、持久化）严格规矩，看板层（前端、接口）明显放松。分界线不是能力，是"当时赶不赶"。

## 二、问题清单（按类别）

标记说明：**已复核** = 我逐条看过代码或跑过复现；未标记 = 排查结论，可能有误报。

### A. 数据正确性（会算错账、写坏数据）

#### A1. 模拟盘可以超额买入（双花）

- **问题**：下单时"读余额 → 计算 → 写回"这三步之间没有任何保护。数据库默认模式下，"读"这一步根本不在事务里。
- **原因**：代码默认"同一时刻只会有一个下单请求"。同一个文件里另有地方**正确加了锁**，这处漏了。
- **后果**：两个请求同时下单，都读到同一份余额、各自扣一遍，实际只扣一次钱却成交两次。资金账目错，且是"越用越错"的静默错误。
- **措施**：读余额之前先取得写锁（已修）。**已复核**：并发 5 个线程下单，现在只成交 1 笔。

#### A2. 价格为 0 的行情能通过校验，导致 0 元成交

- **问题**：行情批次发布前的质量检查只验证"价格不是空值"，**没有验证"价格大于 0"**。而盘前/数据源异常时，接口确实会返回 0。
- **原因**："非空"被当成了"有效"。这类判据写起来顺手，但漏掉"合法的坏值"（0、负数、空字符串）。
- **后果**：0 元成交 → 不扣现金、成本记 0、持仓凭空出现；账户总资产、盈亏全部失真，而且**没有撤单机制**。
- **措施**：质量检查与下单校验都要求"大于 0"。

#### A3. 公告表去重完全失效

- **问题**：公告表的唯一标识包含"发布时间"这一列，而这一列允许为空。数据库的规则是"空值不等于任何值，包括另一个空值"，所以**没有发布时间的公告永远认为是新的**，每次都插一条。
- **原因**：把"可空列"放进了唯一标识。这是 SQL 的一个经典陷阱，代码本身不会报错。
- **后果**：公告表无限膨胀；展示时按时间倒序取前 30 条，重复项会挤掉真实内容。
- **措施**：该列改为"非空、默认空串"，历史库自动重建去重（已修）。**已复核**：同一条无日期公告连插 3 次，现在只剩 1 行。

#### A4. 多步骤写入没有事务，失败留半截数据

- **问题**：一个业务动作在代码里是好几条数据库写入（例如"把旧偏好标记为失效 + 写入新偏好"），但**每条各自生效**，中间没有任何捆绑。
- **原因**：数据库连接配置成了"每条语句立刻生效"的模式，事务正确性完全依赖"每处手写锁和提交"，记得写的地方对、忘了的地方静默不原子。
- **后果**：中途失败（进程被杀、数据库忙、校验不过）→ 旧的已失效、新的没写入 → **用户的一条记忆凭空消失**，且没有任何报错，因为每条语句自己都是"成功"的。
- **措施**：建立统一的事务入口，把这类"多条写入算一件事"的地方全部纳入（已修 7 处）。**已复核**：嵌套合并、异常整块回滚、独立调用自提交三种语义都验证过。

#### A5. 证据校验漏掉列表型数据

- **问题**：报告里的每个数字都必须能在快照里精确命中，否则判为"编造"。但收集"允许的数字"时，只收集了**单个数值**，把**数值列表**（如"近三年 ROE 序列"）整段跳过了。
- **原因**：类型判断只覆盖了标量类型，没递归处理列表/字典。
- **后果**：模型照抄快照里真实存在的 ROE 序列 → 仍被判为幻觉 → 触发整维重跑 → 最终弃权。**这不是"卡得太严"，是"漏掉了合法来源"**，代价是白烧 token 且拿不到结论。
- **措施**：递归收集所有数值，包含列表与嵌套结构。

### B. 隐私与隔离

#### B1. 专家记忆跨用户泄漏【已复核，实测复现】

- **问题**：给每只股票分配的"研究档案编号"**只包含股票代码**，不含用户身份；而检索专家记忆时的过滤条件只有"哪个专家 + 哪个档案 + 是否成功"，**完全没有用户维度**。
- **原因**：做隔离时想的维度是"专家之间要隔离"（这个做到了，也有测试），**漏了"用户之间要隔离"**。测试里没有任何用户维度的用例。
- **后果**：用户 A 分析某只股票时，专家写入的私有记忆（内容源自 A 的口头要求与偏好）→ 用户 B 之后分析**同一只股票**时，这段记忆被原样注入 B 的分析上下文。**跨用户泄漏成立**，而且系统里没有任何地方会暴露这件事。
- **措施**：档案编号纳入用户身份，或在状态表里加用户列并在检索时强制匹配。**需要先定口径**（是否要兼容已产生的历史数据）。

#### B2. 继承记忆时不校验"父档案"的身份

- **问题**：子任务继承私有记忆时，只按编号取父档案，**不检查这个父档案是不是同一个专家、同一只股票、同一个用户**。而这个父档案编号可以来自**模型生成的参数**。
- **原因**：把"编号"当成了可信输入。当前生产路径没有用到这个能力（潜伏状态），但它是公开接口。
- **后果**：一旦某条路径允许模型自己指定父档案，就能继承任意档案的私有记忆（跨专家、跨用户、跨股票），甚至直接接管别人的会话。
- **措施**：继承前校验父档案的身份三要素，不符则不继承并记审计。

### C. 投研结论可信度

#### C1. 引用校验的兜底方向写反【已复核，实测复现】

见"模式二"。实测结果：**本轮一张卡片都没检索到**，模型编造的两条引用（其中一条在知识库里根本不存在）**原样进入最终报告**。

- **措施**：过滤后为空时不再回头保留假引用，改为降级标记或转弃权。顺带修掉"浅拷贝绕过校验"的问题——改用完整校验重建对象。

#### C2. 结论字段自相矛盾

- **问题**：投票时弃权的专家被排除，所以基本面弃权**不影响评级**；但给用户看的那句话，只要基本面弃权就写死"信息不足，本次不形成方向判断"。
- **原因**：两个字段的生成逻辑分别写在两处，各自看都合理，**没有人检查它们是否一致**。设计文档明确要求"给用户的一句话必须与评级一致"，但没有代码层面的强制。
- **后果**：技术面+情绪面都看多时，出现"评级=买入"配"不形成方向判断"。下游只看评级的消费方（命令行、看板卡片、追踪基线比对）会当成买入结论。同项目另一条路径的处理是"评级=暂不判断"，**两条路径规则不一致**。
- **措施**：统一规则（建议以"暂不判断"为准，与已实现的路径对齐），并给"评级与结论句一致"加校验，让它不可能再矛盾。**需要先定口径**。

#### C3. 消息压缩会丢任务定义与关键数据

- **问题**：上下文压缩时有个"关键消息要保留"的机制，但**全仓从来没有人设置过这个标记**（只有读取），所以该机制从未生效。同时，工具返回的快照数据与普通日志是同样的优先级。
- **原因**：机制写了、参数留了、**但调用方忘了传**。属于"模式一"。
- **后果**：任务定义（目标、必填问题、约束、跨轮记忆）只要不在"最近若干条"窗口内就被直接删掉 → 模型看不到任务要求，表现为答非所问、必填字段缺失、反复被驳回直到轮次耗尽。更严重的是快照数据被压掉后，证据校验要求"数字逐字相等"，模型拿不到原始数字只能凭记忆写 → 必然失败 → 重跑 → 弃权。**"压缩抢走数据 → 模型答错 → 被反复驳回"这条链路是通的。**
- **措施**：任务定义与权威快照打上保留标记；压缩层级不得中途切断结构化数据。

#### C4. 压缩预算与实际配置严重不匹配

- **问题**：压缩模块内部写死了"上下文长度 32768、预留输出 4096"，而四个专家实际允许输出 32768。**预留量比实际允许输出小 8 倍**。
- **原因**：压缩配置与运行配置各自独立、从未对账。
- **后果**：双向都错——真实窗口还很空就触发压缩（白丢信息，叠加 C3）；真要长输出时又可能超限 → 整轮失败且无降级。
- **措施**：压缩配置从运行配置派生，预留量等于实际最大输出。

#### C5. 中文 token 计数低估 3-4 倍

- **问题**：估算长度的公式 `(字符数+3)/4` 是英文经验值，而项目内容**全是中文**（中文大致 1 字 1 token）。
- **原因**：直接沿用了英文场景的通用近似值，没有考虑内容语言。
- **后果**：判定"装得下"但实际超限 → 请求被拒（且这类错误被判定为"不可重试"）→ 整轮失败，四层压缩一层都没来得及跑。
- **措施**：按字符类别加权估算（中文 1、英文 0.25），或接入真实分词器。

#### C6. 模型的推理过程被回传给模型

- **问题**：持久化层特意剥离了模型的内部推理内容（注释里写明了），但**内存中的消息缓存没有剥离**，于是它被原样塞回请求发给模型。
- **原因**：两处序列化路径的处理不一致——一处记得剥、一处忘了。
- **后果**：轻则白烧 token、让长度估算更失真；重则接口直接拒绝（返回 400）。
- **措施**：序列化时永不输出内部推理，或从内存投影阶段就清空。

### D. 流程卡死与状态残留

#### D1. 流程失败后记录永久停在"进行中"【已复核】

见前面"run 为什么永远卡在 running"。要点：**登记之后、失败保护之前**夹着"理解意图、读偏好"这一段，这段出错就没人回来打叉。

- **后果**：这条股票的后续反馈与追踪**永久卡死**（后续操作要求父记录是成功或降级状态），同时库里留下脏记录、没有任何失败审计。
- **措施**：失败保护的起点提前到写完登记之后立刻开始。同类问题在"反馈"流程里也存在（子记录同样卡住）。

#### D2. 被取消的任务永久停在"进行中"

- **问题**：流程只捕获常规异常，**捕获不到"任务被取消"**这一类中断。而超时机制正是靠取消来实现的。
- **后果**：超时或进程中断留下的子任务，状态永远是"进行中"，没有任何回收。
- **措施**：捕获中断信号并把状态写成失败；启动时清扫陈旧的"进行中"记录。

#### D3. 研究任务超时后留下孤儿线程【已复核（机制确认）】

见前面"孤儿线程"的说明。补充根因：**模型调用没有设超时，用的是 SDK 默认的 600 秒**，比 worker 的 8 分钟预算还大，注定被放弃。

- **后果**：看板说"失败、请重跑"，专家库说"成功、记忆已存档"；用户重跑一次烧两遍钱；专家库留下没人引用的孤儿记录。
- **措施**：给模型调用设显式超时；超时走协作式取消（让流程自己把状态写成失败），或用子进程 + 强杀；至少把孤儿线程登记下来做对账。

#### D4. 长任务被重复领取、并行执行

- **问题**：任务记录上有个"更新时间"，超时回收靠它判断。但任务执行期间**没有任何地方刷新这个时间**。而回收阈值（8 分钟）恰好等于 worker 自己的超时。
- **原因**：只考虑了"进程崩溃后需要回收"，没考虑"正常执行但耗时较长"的情形。
- **后果**：**越慢的任务越必然被抢**——两个 worker 并行执行同一个任务，写同一份结果。
- **措施**：执行期间定期续租，且续租只在任务仍是"进行中"时生效（已修）。**已复核**：无心跳时任务被抢走，有心跳时不会。

### E. 两个数据库不一致

#### E1. 用户的口径在传递中静默丢失【已复核】

- **问题**：临时文件（存用户补充口径）用的是**相对于当前工作目录**的路径，而数据库路径用的是**相对于项目根目录**的路径。
- **原因**：路径解析工具已有，但这一处忘了用。
- **后果**：当接口进程和 worker 进程的工作目录不同（文档鼓励分别启动）→ worker 读不到你的口径文件 → **你写的要求被静默丢弃**，分析照常成功，你永远不会知道。同时旧目录里的临时文件永久堆积。
- **措施**：改用统一的路径解析；更彻底的做法是把口径直接存进任务记录（该列已存在却被刻意写成空）。

#### E2. 先提交任务、后写口径文件

- **问题**：接口先把任务写进库里（立刻可被 worker 领取），**然后**才写口径文件。
- **原因**：两步操作的顺序没考虑"中间会被别人插手"。
- **后果**：worker 可能在写文件之前就领走任务 → 读不到口径 → 用默认值执行；若写文件失败（磁盘满/目录只读）→ 返回 500 给用户，但**任务已经入队且会照常执行**，用户以为失败、后台却在跑。
- **措施**：口径与任务在同一个事务里写入，或先写文件、成功后再入队；失败路径要把任务标记为失败。

#### E3. 队列中的任务没有过期处理

- **问题**：超时回收只处理"进行中"的任务，**不管"排队中"的**。而某些启动方式下根本没有 worker 来消费。
- **后果**：该股票的任务永远排队 → 之后对这只票的任何操作都返回"已有任务进行中" → 前端每 2.5 秒轮询一次，永远不会结束。且**没有任何取消任务的接口**。
- **措施**：排超过阈值（如 30 分钟）的排队任务标记失败；提供取消接口；worker 主循环整体包异常保护，避免一崩就死。

### F. 前端体验与状态机

#### F1. 换股票时一个请求失败 → "界面还是旧股票，但已切到新股票"【已复核】

- **问题**：切换股票时并发发多个请求，其中**三个没有失败保护**（另外三个有）。而界面切换动作在请求之前就执行了。
- **原因**：同一个函数里有的请求挂了保护、有的漏了——**不一致**。
- **后果**：点击一只不在当前行情批次里的股票（自选列表用左连接，停牌/退市股仍会显示）→ 某个请求返回 404 → 整个并发块中断 → 界面切过去了、股票编号也换成了新的，**但页面内容还是上一只股票的**。此时点"开始分析"，会对着**新的那只股票**下单——用户以为在分析屏幕上那只。**可能对错误标的下单分析。**
- **措施**：每个请求单独兜底；界面切换放到数据拿到之后；失败时回滚视图或明确提示。

#### F2. 按钮永久禁用的四种路径

- **问题**：界面用"先禁用、拿到状态后再解锁"的模式。但**解锁依赖的那个请求一旦失败，就被静默吞掉**，解锁永不到来。
- **原因**：状态机没有"失败也要推进"的分支；且触发按钮在请求期间不禁用，可以连点。
- **典型触发**：
  - 账户信息请求失败 → 追踪/反馈/下单按钮全部永久变灰（屏幕上明明有完整分析结果）。
  - 失败的任务污染了"当前任务编号" → 后续反馈永远返回 409，反复点击永远失败，必须退出重进页面。
  - 采集行情时一次状态查询失败 → 轮询链断掉、按钮永久变灰，只能刷新页面。
  - 开两个标签页时，一个在采集、另一个刚打开就会读到"采集中"，然后**再也不轮询**，永久变灰。
- **措施**：失败分支也必须推进状态机；按钮在请求期间禁用；增加低频状态自愈；前端建立统一的"定时器 + 请求取消"管理（目前全文件**零取消机制**，这是多数前端缺陷的共同根因）。

#### F3. 跨标的状态污染

- **问题**：轮询逻辑用的是**全局的"当前股票"**，而不是发起时那个股票；切换股票时**不取消任何在途轮询**（全文件没有一个取消定时器的调用）。
- **后果**：A 股票的分析完成后，结果被渲染进**正在查看的 B 股票**页面，并把"当前任务/当前结果"都设成 A 的 → 用户在 B 页面点追踪 → 后端找不到 B 的基线 → 报出原始异常文本。
- **措施**：轮询闭包捕获发起时的股票编号，每轮校验；统一登记并取消定时器。

#### F4. 查看历史版本后，反馈会悄悄基于旧版本分叉

- **问题**：查看历史版本时，"当前结果编号"被改成了那个旧版本，且界面没有任何提示。
- **后果**：接着点反馈 → 新分析从**几天前的旧基线**分叉，覆盖掉最新结论，相当于把结论回退。
- **措施**：区分"展示用版本"与"可反馈的当前版本"；查看历史时禁用反馈或明确提示。

### G. 工程护栏（本次已补一部分）

#### G1. 零 lint / 零 CI / 零依赖版本约束

- **后果**：本次一加检查工具，立刻扫出十来个问题，其中包括**真会导致崩溃的"名字未定义"**（只在字符串注解里出现，任何反射调用都会报错）和"用了但没导入"。依赖全部是**无版本约束**的裸依赖，其中两个以频繁破坏兼容著称——某天早上项目可能直接装不上，而因为没有 CI，你不会提前知道。
- **措施**：(1) 加检查工具并清到零告警（已完成）；(2) 依赖加版本区间（已完成）；(3) 加最小 CI（待做）。

#### G2. 测试默认会访问真实接口、真实花钱

- **问题**：测试框架配置里没有排除"需要真实密钥"的测试，而文档引导用户先配置密钥再运行测试。
- **后果**：裸跑一次测试就真实调用外部接口、消耗额度。
- **措施**：默认排除真实调用类测试，需要时显式开启（已完成）。

#### G3. 死代码与永不生效的样式

- **问题**：例如某个"当前步骤高亮"只加不减；某个"锁定"样式只有半透明效果、**不加"禁止点击"**，所以锁定的按钮仍可点；某段样式依赖的计数器从未被使用；某个键盘事件处理器被连续赋值两次（后者覆盖前者）。
- **后果**：这类问题单独看无害，但会**误导维护者按"看起来的意图"改代码**。
- **措施**：随功能改动顺手清理（不急于专门处理）。

## 三、为什么这些 bug 很难被测试发现

现有测试数量不少（270 个，且大部分是离线可跑的），但这次的多数问题它抓不到。原因是**测试的粒度和问题的性质不匹配**：

| 问题性质 | 测试能发现吗 | 为什么 |
| --- | --- | --- |
| 函数返回错了 | 能 | 这是测试最擅长的 |
| **某段分支从未被触发** | 不能 | 测试只验证"返回什么"，不验证"这段路走过没有"。压缩的保留标记、反馈的"下次生效"标记都属于这类 |
| **两个字段互相矛盾** | 不能 | 评级和结论句各自测都对，没人测"它们俩说法一致" |
| **并发下的时序问题** | 不能 | 单线程测试永远碰不到"两个请求同时读同一份数据" |
| **跨用户的隔离** | 不能 | 测试只覆盖了"专家之间隔离"，没有用户维度用例 |
| **静默降级** | 不能 | 出错了返回空列表，测试看到空列表就认为"正常" |
| **前端状态机卡死** | 不能 | 前端**零测试**（没有任何 JS 测试） |

**可操作的改进方向**（比"多写测试"更有效）：

1. **给"必须生效"的机制加端到端观测**——用审计事件证明它真的被执行过。本次排查中，凡是写了审计的地方行为都能还原，没写的地方就是黑盒。
2. **给"互相矛盾的两个字段"加校验**，让代码层面无法产生矛盾。
3. **补用户维度的隔离测试**。
4. **前端至少覆盖状态机**（失败后按钮是否恢复、轮询是否会停）。
5. **加一条"死分支"检查**：对兜底/保护类分支，用覆盖率或断言证明它会被触发。

## 四、用 AI 写代码的经验教训

你用 Cursor + 模型辅助开发，这次的问题分布里有一些**属于 AI 辅助编程特有的风险**，值得单独记下来：

**1. 防御性代码最容易"看着对、实际错"。**
AI 很擅长写"周全的"防御——留个兜底的标记、加个怕崩溃的后门、包一层异常处理。但：
- 留了标记**忘了在调用方设置** → 机制从未生效；
- 后门**方向反了** → 在最危险的场景放行；
- 异常处理**吞掉了错误** → 故障伪装成"没有数据"。

这些分支人眼极难审查，因为它们**写得像模像样**。而 AI 不会回头验证"这段真的会跑吗"——它只保证"语法正确、看起来合理"。

**2. "看起来完整"给了虚假的安全感。**
一份 270 个测试、有设计文档、有审计事件、有降级和弃权语义的项目，会让人觉得"该考虑的考虑了"。但恰恰是那些"写了却从未生效"的部分最危险——**它们让缺失变成了隐形**。

**3. 冲刺模式下 AI 会放大你的纪律缺口。**
你状态好的时候（内核层）写出了教科书级的代码；赶工时（一天七个提交）AI 顺着你的速度产出，**两套标准就被同时固化进了同一个仓库**。AI 不会说"这个事务要不要加锁"，它会顺着你给的上下文写下去。

**4. 有效的应对方式（本次验证过的）**：
- **让 AI 审查 AI 写的代码**：这次四轮排查全部由独立审查完成，抓出了作者本人（包括我）看不到的问题——我自己本轮引入的一个变量名写错，就是审查抓出来的。
- **上工具护栏**：lint 是成本最低的一个，十分钟能扫出十来个真问题。
- **追问"这段生效了吗"**：对每段防御性代码，要求用日志或审计证明它被执行过。
- **不要在同一天既赶功能又改并发/事务**：这次问题最密集的区域，恰好是"当天七个提交"的产物。

### 需要先拍板口径（3 项）

1. **跨用户隔离怎么改**：档案编号纳入用户身份，还是给状态表加用户列？要不要兼容已有历史数据？

## 六、一句话总结

**问题数量是四轮深挖的结果，不必恐慌；但根因只有 5 个模式——"写了没验证它生效"、"兜底开成后门"、"异常被吞掉"、"并发默认不会发生"、"缺少护栏和节奏"。**

这 5 个模式不是能力问题，是**机制问题**，而且每一个都有便宜且确定的应对方式。真正值得记住的一条是：**这次最有价值的发现（压缩机制从未生效、反馈写进去没人读、引用兜底放行、跨用户泄漏），没有一条是"逻辑写错"，全都是"写了但没人在真实流程里走过一遍"。**
